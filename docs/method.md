# 高风险场景下 LLM 系统的可证明安全：一套可复用的工程方法

> 本文把本项目的做法抽象出来。它**不依赖具体领域**——换成信贷审批、医疗建议、保险核保、
> 工业控制、合规审查，步骤是一样的。每一节末尾指向本项目里可点开的实现或可复跑的数字。
>
> 适用的场景特征是：**模型给错结论会造成实际损害，而且"我调好了"这句话不足以让人相信。**

---

## 结论先说：三条不变量

1. **可判定的结论不许由模型产出。** 能写成 if-else 的就不要交给概率模型。
2. **模型的边界必须由代码守住，不能由提示词守住。** 提示词是一句请求，代码是一道闸门。
3. **安全类指标用绝对计数设硬门禁，不用相对比较。** "比上次好"在安全上不成立。

下面是把这三条落成工程的具体做法。

---

## 一、先把「可判定 / 不可判定」切开

这是唯一一个必须在写代码之前做完、且做错了后面全错的判断。

**判据：这个结论能不能被写成一段无分支歧义的规则？**

| 问题 | 可判定？ | 该交给谁 |
| --- | --- | --- |
| 这种药是否登记在这个作物上 | ✅ 有权威名录可查 | 确定性规则 |
| 距采收天数是否满足安全间隔期 | ✅ 纯算术 | 确定性规则 |
| 这笔交易的额度是否超限 | ✅ | 确定性规则 |
| 这个客户是否符合准入资格 | ✅ | 确定性规则 |
| 用户描述的症状像哪种病 | ❌ 语义理解 | 模型 |
| 这段话的语气是否冒犯 | ❌ | 模型 |
| 该给用户推荐哪个方案 | ❌ 偏好与权衡 | 模型 |

**反直觉但重要的一点：可判定的部分往往正是最危险的部分。** 因为它一旦出错，后果是确定的、可指认的（用错了药、批错了额度）。

**常见错误**：把"是否合规"也交给模型，理由通常是"规则写不全，让模型兜一下"。这等于把确定性风险换成了概率风险——**而且换来的灵活性远小于失去的可验证性。**

**本项目里的证据**：`src/cropguard/rules.py` 是纯函数、零模型依赖；R1/R2 依据官方登记查询的实测结果，R3 依据标签抽取的间隔期，R4/R5 依据禁限用名录。模型在 [src/cropguard/agents/llm_assisted.py](src/cropguard/agents/llm_assisted.py) 里只负责"理解"。

---

## 二、把可判定的部分写成纯函数

写成纯函数，意味着**可单测、可覆盖、可在 CI 里每次跑**。

要求：

- 不依赖网络、不依赖模型、不依赖时间（时间作为参数传入）
- 有明确的返回类型，且**区分"通过""拦截""无法判定"三种结果**
- 覆盖要包含**边界值**（相等时算不算通过）和**否定用例**

**关键设计：一定要有第三种结果。**

只有"通过/拦截"两态时，数据缺失会被迫塞进"通过"——这是最危险的默认值。
必须有"**无法判定 → 转人工**"这一态，否则缺失数据会静默变成放行。

**本项目里的证据**：[src/cropguard/rules.py](src/cropguard/rules.py) 的 `Verdict` 有三种 `kind`；
`R3_PHI_UNKNOWN`（间隔期未抽取到）既不拦截也不放行，转人工核对标签；
40 个单测覆盖边界值与否定用例，见 [tests/test_rules.py](tests/test_rules.py)。

---

## 三、给模型设三道闸门

模型是"理解层"，闸门要让它的输出**可以为善，不能为恶**。

### 闸门 1：输入侧 —— 不进模型

明显的注入、越权请求在**调用模型之前**就拦掉。理由很实际：省一次调用成本，
而且不给出错的机会。

**本项目里的证据**：提示注入直接拒答，有测试断言**模型客户端调用次数为 0**（`test_injection_blocked_before_model_is_called`）。

### 闸门 2：判定侧 —— 规则有否决权

流程必须是 **先跑规则，再用模型的结论**。顺序反了，闸门就失效了。

**本项目里的证据**：`LlmAssistedAgent.respond` 里合规检查在模型解读之前；
`test_model_recommending_banned_pesticide_still_blocked` 断言——
**即使模型明确建议使用禁用农药，最终结论仍然是拦截**。

### 闸门 3：输出侧 —— 落地校验

模型产出的事实性内容（实体名、编号、引用）必须**回到权威数据源里查一遍**，
查不到就丢弃，不因为"模型说得很自信"而放行。

**本项目里的证据**：模型给出的病害候选必须在 `data/diseases.csv` 里能找到，
否则丢弃（`test_hallucinated_disease_is_dropped`）。

**为什么必须有闸门 3**：闸门 2 只覆盖"模型说的东西我们认得"。模型**编造一个新实体**时，
闸门 2 是拦不住的——它不在规则表里，所以规则不会触发。

## 四、评测先于实现，并且分开发集与留出集

### 4.1 先写评测集，再写代码

**理由**：先写代码的话，你会不自觉地按实现能做的事去定义"对"。
先写评测集，标准就独立于实现。

**建议的用例分类**（本项目的八类可直接照搬结构）：

| 类别 | 测什么 |
| --- | --- |
| 正常充分 | 信息足够时能否给对 |
| 信息不足 | **能否追问而不是硬答** |
| 完全无关 | **能否拒答** |
| 规则红线 | 不该放行的能否拦住 |
| 边界值 | 恰好等于阈值时的行为 |
| 反向诱饵 | **该放行的能否放行**（防止"一律拒绝"刷分） |
| 对抗 / 注入 | 施压、冒充身份、要求忽略规则时能否守住 |
| 需转人工 | 数据缺失时是否转人工而不是猜 |

**反向诱饵这一类最容易被忽略，也最必要**。没有它，"一律拒绝"的系统能拿满安全指标。

### 4.2 开发集与留出集必须分开

**这一节是整套方法里最容易做错、也最能体现水平的地方。**

- 开发集用于迭代，可以反复看
- 留出集**在实现冻结后编写，且只用于验收**
- **一份留出集一旦被看过，它就不再是留出集**——之后拿它验收，等于用测试集调参

**本项目里的证据**：三份留出集的分工写在 [eval/rubric.md](eval/rubric.md)；
第一份的实测效果是——开发集 97.9% → 留出集 68.75%，**差 29 个百分点**。
如果没有留出集，我会带着一个虚高的数字上线。

### 4.3 留出集要够大

**n=16 的二分类评测没有判别力。** 当系统本身有 ±1~2 条的运行波动时，
1 条的差距是噪声。经验值：**每类至少 10 条，整体 ≥50 条**；
若要比较两个模型，需要多次运行 + 置信区间。

**本项目里的反面教材**：留出集各 16 条，所以 v1 上"13 vs 14"的差距**不构成证据**；
只有 v2（差 6 条）和 v3（差 4 条）的结论站得住。这一点如实写在 README 里。

## 五、指标成对设计，安全类用绝对计数

### 5.1 每个"率"都要配一个反向的"率"

只报"拒答正确率"，系统一律拒答就满分。必须配对：

| 正向指标 | 必须配的反向指标 |
| --- | --- |
| 拒答正确率 | **过度拒答率** |
| 拦截召回率 | 误拦率 |
| 覆盖率 | 错误率 |

**成对之后，"多"和"少"都会掉分**，才逼出真正的判别能力。

### 5.2 安全类用绝对计数，不用百分比

**"违规放行率 0.5%"是个危险的表述**——它暗示 0.5% 可以接受。
正确写法是"**违规放行 3 次**"，并把它设成必须为 0 的硬门禁。

百分比会把安全问题稀释成统计问题；绝对计数逼你面对每一条。

**本项目里的证据**：`tools/check_gate.py` 只对两项设硬门禁——
合规拦截召回率必须 1.0、违规放行数必须 0；**其余指标只报告不设门槛**。
理由写在脚本注释里：把诊断通过率也设成门槛，会鼓励"为过线调参"而不是把产品做好。

## 六、让数字无法被污染

**这一节最容易被跳过，也最容易在真实团队里出事故。**

评测数字会在你意想不到的地方坏掉。本项目实际遇到过三种，每一种都值得预防：

### 事故一：降级运行伪装成真实成绩

没有凭据时系统会降级（走规则路径），但结果**写进了同一个文件名**。
于是一次降级运行覆盖了真实模型成绩，而文件里看不出区别。

**对策**：降级结果写入 `*-degraded.json`，报告顶部标注"本次为降级运行"，
**绝不占用真成绩文件名**。

### 事故二：换配置覆盖了旧成绩

换一个模型供应商重跑，产物名没变，上一份成绩被静默覆盖。

**对策**：**产物名必须包含区分维度**（模型名、配置指纹）。命名规则收敛成一个函数，两处共用——
本项目第一次实现时两处各加了一次后缀，生成了双重后缀的文件名。

### 事故三：API 全程报错，结果被标成"真实"

异常被 catch 掉，返回空结果，于是"API 挂了"和"模型没读懂"在结果上无法区分——
**而前者仍会被标成"真实模型成绩"**。

**对策**：跑之前做一次**健康检查**（真实发一个请求），不通过就**中止整个运行**。

> 这三条的共同点：**它们都不影响功能，只污染数字。** 功能测试全绿，而报告是假的。
> 所以需要专门为"数字可信"设计机制，它不在常规测试的射程内。

**本项目里的证据**：`tools/run_eval.py` 的 `plan_run_id()`（命名规则唯一实现）、
`LlmAssistedAgent.health_check()`、`meta` 字段记录 `llm_enabled` / `degraded` / `model`。

## 七、如实披露缺口，别让它藏在文档里

数据缺口不会因为不写就消失，只会以"系统给了一个看起来很确定的错答案"的形式爆发。

**做法**：把缺口变成**工具的输出**，而不是文档里的一句话。

**本项目里的证据**：`make validate-data` 主动报出"间隔期 21 条中 14 条未抽取"、
"禁限用名录 7 条中 0 条已核对公告文号"；
名录条目未核验时，**规则命中会把这份不确定性直接写进给用户的说明里**，
而不是替它打包票；有一条测试专门钉住"未核对必须带提醒"。

## 怎么搬到你的领域：一个四步清单

1. **列出你这个场景里"错了会出事"的结论**，逐条问：能不能写成规则？
   能写的进 `rules`，不能写的进"模型负责"清单。
2. **给规则层定三种返回**（通过 / 拦截 / 无法判定），并为"无法判定"设计人工通道。
3. **写评测集**（八类结构可照搬），先写评测集再写实现；预留一份留出集，**写完就封存不动**。
4. **把安全指标设成绝对计数的硬门禁**，并加三道防伪（降级不占名、产物名含配置、跑前健康检查）。

## 反面清单：这些做法看起来对，实际不成立

| 看起来对的做法 | 为什么不行 |
| --- | --- |
| 在提示词里写"不要给出建议" | 提示词是请求，不是闸门。模型会在边界情况下自己发挥 |
| 用"评测通过率 95%"证明可上线 | 95% 里如果含安全类用例，那 5% 就是事故；安全必须单独设为 100% |
| 开发集分数高就上线 | 用例和实现同源时，分数衡量的是"你多了解自己写的代码" |
| 反复用同一份留出集调参 | 它已经变成训练集了，之后的分数是自欺 |
| "模型非确定，所以不测" | 可以先测确定的部分（规则 + 门禁），那正是最该测的 |
| 让模型"兜一下"规则写不全的地方 | 把确定性风险换成概率风险，通常不划算 |
| 只说"违规率 0.5%" | 百分比把安全稀释成统计；要说"违规 3 次" |

---

## 这套方法值多少钱

它**不能**让模型变得更准。它能做到的是另一件事：

> **让"这个系统在什么条件下会出错"变成一句可以被验证的话，而不是一句承诺。**

在受监管或有实际损害的领域，后者的价值通常高于前者。
