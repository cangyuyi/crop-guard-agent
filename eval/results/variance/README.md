# 模型实现的运行间波动（证据留档）

**结论：确定性实现重跑必然一致；模型实现同代码同用例也会波动。**

| 文件 | 运行 | 开发集通过 |
| --- | --- | --- |
| `dev-llm_assisted-run1.json` | 第 1 次 | **44 / 48** |
| `dev-llm_assisted-run2.json` | 第 2 次 | **45 / 48** |
| `dev-llm_assisted-run3.json` | 第 3 次（也是规范文件 `../dev-llm_assisted.json` 的来源） | **45 / 48** |

对照：`rule_based` 在同一份开发集上恒为 **44 / 48**（`../dev-rule_based.json`），
重跑任意多次结果相同——因为它不调模型。

## 为什么留这份档

三次运行使用**完全相同的代码、完全相同的用例**，请求里也设了 `temperature=0`，
结果仍在 44–45 之间浮动。原因在于推理模型本身的采样与推理路径不保证确定性。

这件事有三层含义：

1. **README 里模型实现的分数必须写成区间，不能写成单点。** 写一个精确数字会给人
   "可复现"的错觉——那不是事实。
2. **不能拿单次模型分数去做回归对比。** 差一条可能只是噪声。安全类指标因此被设计成
   "必须恒为 1.0"的硬门槛，而不是"比上次高"的相对比较。
3. **这反过来印证了架构选择**：合规判定不交给模型，所以它不受这份波动影响——
   三个实现、三个数据集上，合规拦截召回率始终 1.0（naive 除外，它没有合规层）、
   违规放行数始终 0。

> 复现：配好 `CROP_GUARD_LLM_*` 后多次执行
> `python3 tools/run_eval.py --agent llm_assisted --run-id <name>`，
> 比较 `summary.passed`。
